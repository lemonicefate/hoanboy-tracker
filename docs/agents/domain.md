# Domain docs

This is a single-context project: the root `CONTEXT.md` is the glossary and `docs/adr/` contains architectural decisions.

Before exploring an area, read the glossary and relevant ADRs. Use defined terms in code, specs, issues and tests. Explicitly surface conflicts with an ADR instead of silently overriding it.

If a referenced domain document is missing, proceed; domain-modeling creates documents when terms or decisions are resolved. Keep implementation plans out of the glossary.
