# HOANBOY 體脂量測歸檔與離線報告 MVP

狀態：需求與分層測試方案已確認；待設定 issue tracker 後發布並套用 ready-for-agent。

## Problem Statement

診所目前需要手機掃 QR、傳 LINE，再用電腦查看體脂報告，人工步驟多，難以依病人保存及比較歷次量測。體脂機以輸入的手機識別，診所以病歷號識別，不能直接視為同一個鍵。診所需要在電腦快速歸檔、查閱、追蹤減重變化，並在設備關機或沒有網際網路時重印完整報告。

## Solution

建立診所本機應用程式，以瀏覽器操作本機後端，透過區網唯讀取得 HOANBOY 370 量測，保存原始資料並轉換為有來源與單位的欄位。人員手動同步、人工選擇病人歸檔，以病歷號管理病人。

病人追蹤頁提供最新核心數值、歷次明細、體重及體脂率曲線；完整報告另頁，保留原廠十區資訊與近似版面，可離線查看、列印。第一版限單機、一台設備、一個操作帳號；架構預留多電腦及定時同步，兩者不列首版功能。

使用者已同意跳過本次新量測的紙本核對，因此可繼續開發。未驗證的代碼與判定不得臆造；完整報告正確性仍是最後驗收條件。

## User Stories

1. As a 診所人員, I want a 本機登入入口, so that 病人資料不會直接公開。
2. As a 診所人員, I want a 手動同步按鈕, so that 我能在量測後取得設備資料。
3. As a 診所人員, I want a 首次同步現存歷史的功能, so that 設備仍保存的紀錄可以逐步歸檔。
4. As a 診所人員, I want a 同步結果摘要, so that 我知道新增、更新與失敗狀態。
5. As a 診所人員, I want a 最後成功同步時間, so that 我能判斷資料是否已取得。
6. As a 診所人員, I want a 可安全重試的同步流程, so that 重複操作不會產生重複量測。
7. As a 診所人員, I want a 明確的設備離線提示, so that 我知道同步失敗且仍可查看既有資料。
8. As a 診所人員, I want a 待歸檔清單, so that 新量測不會被錯誤自動分配。
9. As a 診所人員, I want a 量測時間、來源識別與核心數值摘要, so that 我能確認正確量測。
10. As a 診所人員, I want a 人工建立病人的功能, so that 首次來診者可以立即歸檔。
11. As a 診所人員, I want a 唯一病歷號檢查, so that 相同病人不會因重複病歷號建成兩份資料。
12. As a 診所人員, I want a 病歷號、姓名與手機搜尋, so that 我能迅速找到病人。
13. As a 診所人員, I want a 來源手機候選提示, so that 我可減少搜尋操作但仍親自確認病人。
14. As a 診所人員, I want a 容許共用或更換手機的病人資料, so that 不會因手機關係自動合併病人。
15. As a 診所人員, I want a 明確的人工歸檔操作, so that 一筆量測只歸屬一位已確認病人。
16. As a 診所人員, I want a 解除與重新歸檔功能, so that 配錯病人可以修正。
17. As a 診所人員, I want a 歸檔修改紀錄, so that 能追查修正前後的歸屬。
18. As a 診所人員, I want a 忽略及恢復待歸檔量測的功能, so that 測試或暫時無法識別的紀錄不妨礙工作。
19. As a 診所人員, I want a 病人最新數值摘要, so that 進入病人頁即可了解最近量測。
20. As a 診所人員, I want a 依量測時間排序的歷史列表, so that 可快速查看過往紀錄。
21. As a 診所人員, I want a 單筆量測明細, so that 可以查看當次結果、單位及缺漏狀態。
22. As a 診所人員, I want a 保留同日多次量測的歷史, so that 重測不會被日期去重吃掉。
23. As a 診所人員, I want a 體重曲線, so that 可以觀察減重變化。
24. As a 診所人員, I want a 體脂率曲線, so that 可以觀察身體組成變化。
25. As a 診所人員, I want a 與前次及首次量測的差值, so that 可快速比較進度。
26. As a 診所人員, I want a 缺值與未驗證欄位的清楚提示, so that 不會把零或猜測值當成真實結果。
27. As a 診所人員, I want a 獨立完整報告頁, so that 查閱單次報告與追蹤歷史互不混淆。
28. As a 診所人員, I want a 接近原廠十區版面的列印報告, so that 可延續診所既有報告流程。
29. As a 診所人員, I want a 報告中的歷史摘要, so that 可在紙本查看截至該次量測的變化。
30. As a 診所人員, I want a 設備關機或網際網路中斷時可重印的報告, so that 過去紀錄不依賴設備或雲端持續可用。
31. As a 診所人員, I want a 保持原始輸入與已保存報告版本的機制, so that 修改病人資料或新增量測不會默默改写舊結果。
32. As a 診所人員, I want a 日常自動備份及手動備份功能, so that 資料可以復原。
33. As a 診所人員, I want a 經驗證的還原流程, so that 病人、量測、歸檔關係與報告能一起恢復。
34. As a 診所人員, I want a 快速的病人搜尋與開頁, so that 診間操作不被等待打斷。
35. As a 診所負責人, I want a 可擴充為多電腦與固定頻率同步的架構, so that 首版跑通後不必重寫核心流程。

## Implementation Decisions

- 採本機後端、瀏覽器前端與 SQLite；首版後端僅供本機操作。未選定前後端框架，實作時依 Windows 部署便利性決定。
- 所有資料庫存取經後端；未來其他電腦連主機服務，不以網路共享檔案方式開啟 SQLite。
- 模組分為設備讀取、同步、病人與歸檔、查詢與追蹤、報告、備份。以單一應用服務公開介面整合，不拆成微服務。
- 設備介接唯讀。現有除錯介面需先選資料庫再讀 bodyparm，可能存在共享選庫狀態；序列化本程式的讀取並驗證回應 schema、成功狀態與列寬。其他客戶端干擾仍需防範。
- 設備讀取介面輸出來源 schema、原始列與取得時間；由同一同步工作供手動操作及未來排程呼叫。禁止重疊同步。
- 公開介面涵蓋登入、啟動／查詢同步、建立／搜尋／修改病人、待歸檔查詢、歸檔／解除／重新歸檔、忽略／恢復、歷史與趨勢、報告產生／重印、備份／還原。具體 URL 不在本規格鎖定。
- 病人有內部穩定識別、唯一字串病歷號、姓名與手機；保留病歷號前導零。手機不設唯一限制，來源 username 不強制視為有效手機。
- 保存設備識別、來源量測鍵、原始快照／版本、原始量測時間、取得時間、正規化結果、欄位來源、單位、映射版本與驗證狀態。設備 uid 為候選来源鍵，不等同病人鍵。
- 去重以設備來源鍵與內容變更檢查為基礎；相同來源與內容重讀不新增。同鍵內容不同時保留版本並標記變更；在清庫後識別重用未驗證前，不把所有同鍵變更自動歸入舊病人。
- 缺值與解析失敗不得轉成零；未知欄位保留原始資料，必要欄位異常須有可見提示。不得憑陣列固定索引解析，需以當次 schema 對應。
- 一筆量測最多歸屬一位病人；歸檔修改記錄操作者、時間及前後歸屬。取消歸檔回待歸檔，忽略可恢復，不提供永久刪除介面。
- 核心指標為量測時間、體重、BMI、體脂率；趨勢以所有有效已歸檔量測建立，保留同日重測，不平均或補值。單位、欄位意義未核對者不作正式趨勢結果。
- 日期按設備原始時間保存並另存來源時區與校準狀態；顯示採台灣時間的產品需求不等於設備時鐘已驗證。歷史結果保留當次年齡、身高等輸入，不用現況重算。
- 完整報告保留十區：人體成分、肌肉脂肪、肥胖、內臟脂肪、節段肌肉與脂肪、歷史趨勢、體型、綜合評估、重量控制及健康評分。
- 初稿採 A4 直式單頁、左右兩欄；重現區塊順序、資訊層級、圖表及必要說明，不要求逐像素一致。實際紙張與列印可讀性仍須驗收。
- 報告表頭使用歸檔病人的病歷號與姓名；生理輸入取當次量測。來源手機不替代病歷號。
- 腰臀比不能因範本百分比標籤而乘 100；節段脂肪本例為 kg。骨骼肌使用骨骼肌欄位，不能以總肌肉量替換。皮下脂肪率來源拼字與等級欄前綴不同，需逐欄明列。
- 報告保留骨骼肌歷史摘要，但獨立追蹤頁第一版只有體重與體脂率曲線。報告歷史截止於該次量測，保存選用量測、模板與映射版本及必要本機資產，使離線重印不依賴雲端。
- 重新歸檔後不得沿用舊病人報告；需可識別舊版失效並重建正確報告、保存修正紀錄。
- 未知評估代碼、體型代碼與節段標準判定不自行推算。開發期間可顯示未驗證狀態，但不以空白占位或猜值宣稱完整報告完成。
- 每個有變更的使用日自動備份，保留最近 30 份，提供手動備份與隔離還原驗證。備份包含病人、原始量測、歸檔紀錄與報告資產；正式使用前配置另一儲存裝置。
- 原始病人資料、照片、QR 私密連結與憑證不進 Git、一般日誌、issue 或未確認第三方。正式使用前限制設備除錯介面只允許指定主機存取，不開放外網。

## Testing Decisions

- **採用方案：**主要測試邊界設在本機後端公開應用 API，以模擬設備讀取器及真實暫存 SQLite 驗證外部可觀察行為；少量瀏覽器測試驗證登入、關鍵操作、列印與離線。使用者授權採用常見分層做法，代理已據此選定，不需再次確認。
- 此方案可快速而穩定地驗證資料行為，但模擬設備不能保證真機協定、時鐘、重啟或新量測行為，後端測試不能保證瀏覽器互動及印表機輸出。因此保留實機與實際列印验收；測試通過不能填補未知原廠判定規則。
- 分層原則參考 Microsoft Azure Well-Architected 的測試指引：https://learn.microsoft.com/en-us/azure/well-architected/design-guides/testing 。以 API 整合測試為本專案主要邊界是因資料歸檔與保存風險較高，並非宣稱所有業界專案皆採同一比例。
- 好的測試檢查輸入操作與可見結果、持久化與可復原性，不檢查內部方法呼叫次數、私有函式或特定 SQL 寫法。
- 專案目前只有唯讀抓取與資料檢查腳本、需求文件及 ADR，沒有應用 API、既有測試框架或可沿用的端到端測試；不虛構測試先例。
- 同步：首讀與增量、重讀去重、同鍵變更、同日多筆、離線／逾時、錯誤 schema、缺值、來源時區不明、重疊同步。核對失敗不污染既有歸檔資料。
- 病人及歸檔：病歷號唯一與前導零、共用手機、非手機來源字串、錯誤歸檔修正、忽略恢復、病人之間資料隔離及操作紀錄。
- 查詢與趨勢：正確時間排序、每點與明細一致、首次／前次差值、無資料／單筆／同日重測／缺值，不把缺值連成假測量點。
- 報告：十區內容、已核對來源值與單位、版本可重現、歸檔修正後的身分一致性、關閉設備與外網後仍可查看及列印、A4 預設無截斷且可讀。
- 備份還原：在隔離位置恢復後，病人、量測、關聯與離線報告完整；備份失敗需可見，不能回報假成功。
- 效能：用 1,000 位虛構病人與 20,000 筆虛構量測，目標電腦暖機後常用搜尋及病人頁查詢各不超過 2 秒，不含設備同步。
- 實機驗收：新量測新增已觀察一次；仍需重測、設備重啟、時鐘／時區與同次完整報告核對。使用者暫緩本次列印核對，不等同這些測試已通過。
- 自動化測試使用虛構資料；真實資料核對留在本機私有儲存區。撰寫本規格不代表已實作或執行上述測試。

## Out of Scope

- 首版多電腦開放、跨診所、遠端存取、員工個別帳號及多角色權限。
- 固定頻率同步、自動病人歸檔、兩項以外的互動趨勢曲線。
- 病人名冊批次匯入、病歷系統串接、LINE／QR 整合、手機應用程式。
- 以人工匯入取代區網直讀驗收、尋回設備已刪歷史、追溯 LINE 舊報告。
- 自行重算體脂、醫療判讀、減重建議、發明原廠演算法或節段正常範圍。
- 設備資料寫入或遠端重啟、雲端報告連結作為離線保存的替代、永久刪除介面。
- 字型與間距逐像素複製。原廠完整資訊與正確判定仍屬範圍內。
